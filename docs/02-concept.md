# 3. Концепция

Информационная система персонального контроля питания и физической активности NutriAI Tracker представляет собой распределенный комплекс, состоящий из трех взаимосвязанных компонентов, работающих как единое целое. Мобильное приложение (Android/Java) является клиентским интерфейсом для пользователя. Серверная часть (Linux/FastAPI/Python) выполняет роль вычислительного ядра, обрабатывающего данные и взаимодействующего с ИИ-агентом. Настольный модуль (Raspberry Pi/Linux/Python/GPIO) представляет собой программную эмуляцию «умного автомата перекусов», который управляется командами с сервера. Все три части обмениваются данными по сети, обеспечивая сквозной контроль питания и активности.

Система предназначена для ведения дневника питания, хранения показателей пользователя и формирования персональных рекомендаций с применением ИИ-агента.

ИС NutriAI Tracker должна предоставлять возможность:
- посетителю проходить регистрацию по электронной почте или через поддерживаемый внешний сервис;
- пользователю авторизоваться по электронной почте или через поддерживаемый внешний сервис;
- пользователю создавать и редактировать профиль, указывая возраст, рост, вес и образ жизни;
- пользователю выбирать цель: снижение веса, набор мышечной массы, поддержание веса или оздоровление сердечно-сосудистой системы;
- пользователю просматривать календарь и выбирать дату для заполнения или просмотра данных;
- пользователю вносить за выбранный день сведения о весе, количестве шагов, среднем, минимальном и максимальном пульсе, а также описывать свое самочувствие;
- пользователю загружать фотографии приемов пищи;
- ИИ-агенту анализировать фотографии еды и оценивать состав блюда, размер порции и его КБЖУ;
- системе рассчитывать рекомендуемую суточную норму КБЖУ с учетом профиля, цели и физической активности пользователя;
- системе сравнивать фактические показатели питания с рассчитанной нормой и определять дефицит или избыток калорий, белков, жиров и углеводов;
- ИИ-агенту формировать рекомендации по питанию и физической активности, а также предлагать блюда и рецепты;
- пользователю вручную изменять определенные ИИ-агентом массу блюда и значения КБЖУ;
- системе автоматически пересчитывать суточную статистику после ручной корректировки;
- системе сохранять итоговые данные за день и предоставлять пользователю доступ к истории питания, активности, самочувствия и изменения веса;
- пользователю инициировать запрос на перекус через интерфейс настольного модуля (нажатие виртуальной кнопки);
- системе обрабатывать этот запрос, проверять текущий дневной баланс КБЖУ и принимать решение о разрешении или блокировке;
- системе передавать команду на настольный модуль для программного изменения состояния виртуальных элементов: открытия/закрытия заслонки выдачи и включения зеленого (разрешено) или красного (запрещено) светового индикатора.

Создаваемая ИС будет работать с базой данных профилей пользователей, целей, дневных записей, показателей физической активности, сведений о приемах пищи и результатов анализа. Данные каждого дня связываются с конкретным пользователем и календарной датой.

ИИ-агент формирует оценочные значения на основании переданных фотографий и пользовательских данных. Результат анализа не считается безусловно точным: пользователь может исправить массу блюда, калорийность и количество белков, жиров и углеводов. После сохранения изменений система использует скорректированные значения при расчете итогов дня.

В границу системы входят авторизация, ведение профиля, постановка цели, прием и хранение пользовательских данных, загрузка фотографий, взаимодействие с ИИ-агентом, расчет дневной статистики, ручная корректировка и хранение истории. Также в границы системы входит логика проверки дневного лимита калорий при запросе перекуса и программное управление виртуальными элементами настольного модуля. Внешние сервисы авторизации и сервис ИИ являются взаимодействующими с системой внешними компонентами. Медицинская диагностика, назначение лечения, непосредственное измерение пульса и физической активности, а также фактическое выполнение рекомендаций (и физическое извлечение продуктов из автомата) находятся за границей системы.

# 4. Нефункциональные требования

Нефункциональными требованиями к ИС являются:

**Требования к производительности:**
1. Результат анализа ИИ-агента должен быть получен не позднее чем через 15 секунд после отправки данных.
2. Обработка фотографий не должна блокировать остальные функции системы.
3. Время отклика программного эмулятора настольного модуля (от нажатия виртуальной кнопки до проверки лимита на сервере и отображения результата в виртуальном интерфейсе) не должно превышать 2 секунд.
4. Передача данных между мобильным приложением, сервером и настольным модулем должна осуществляться без задержек, заметных для пользователя.

**Требования к интерфейсу:**
1. Интерфейс мобильного приложения должен корректно отображаться на экранах смартфонов с различным разрешением и плотностью пикселей.
2. Интерфейс программного эмулятора настольного модуля должен содержать виртуальную кнопку, графическую заслонку и цветовой индикатор (зеленый/красный).
3. Заполненные дни календаря должны визуально отличаться от незаполненных.
4. Названия полей и действий должны соответствовать терминам предметной области.
5. Сообщение об ошибке должно указывать поле и причину ошибки.

**Требования к надежности:**
1. Сохраненные данные должны оставаться доступными после завершения работы пользователя или перезапуска сервера.
2. Ошибка анализа или сохранения не должна приводить к потере ранее сохраненных данных.
3. Дневная запись должна сохраняться целиком, без частичного изменения данных.
4. При потере сетевого соединения программный эмулятор должен по умолчанию отображать блокировку выдачи (виртуальная заслонка закрыта, горит красный индикатор) в целях безопасности.

**Требования к безопасности:**
1. Доступ к системе должен предоставляться только после авторизации.
2. Пользователь должен иметь доступ только к собственному профилю и дневным записям.
3. Учетные данные и персональные сведения должны передаваться по защищенному соединению (HTTPS).
4. Запросы от программного эмулятора к серверу должны авторизовываться (например, по токену), чтобы предотвратить несанкционированное изменение статуса виртуальной заслонки.

**Требования к совместимости:**
1. Система должна обрабатывать изображения в форматах JPEG, PNG и WEBP.
2. Мобильное приложение должно корректно работать на устройствах под управлением Android (начиная с определенной версии, например, Android 8.0 и выше).
3. Программный эмулятор настольного модуля должен корректно работать в среде Raspberry Pi с использованием стандартных библиотек Python и интерфейса GPIO.

**Требования к реализации:**
1. Серверная часть должна быть реализована с использованием Python и FastAPI.
2. Данные должны храниться в PostgreSQL.
3. Фоновые задачи обработки фотографий должны выполняться с применением Celery и Redis.
4. Клиентская часть (мобильное приложение) должна быть реализована на языке Java для платформы Android.
5. Программный эмулятор настольного модуля должен быть реализован на Python с использованием библиотек для работы с GPIO.
6. Взаимодействие клиентской и серверной частей, а также сервера и настольного модуля, должно выполняться через REST API.
7. Компоненты системы должны поддерживать запуск с использованием Docker Compose (для серверной части) и стандартных средств сборки для Android и Raspberry Pi.
